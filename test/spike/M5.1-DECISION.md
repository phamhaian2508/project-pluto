# M5.1 technical decision: resumable EVM checkpoints

Status: **accepted for M5 implementation**  
Selected direction: **1A - maintain a small fork/patch of geth's interpreter loop**

## Decision context

M5 must resume inside a transaction from the checkpoint immediately before a
failed speculative read. Replaying an entire transaction or call frame is not
the requested result. Three isolated spikes used the same sample contract; none
is connected to Pluto's production executor.

## Comparison

| Criterion | 1A: geth interpreter fork | 1B: call-frame boundary | 1C: minimal interpreter |
|---|---|---|---|
| Resume inside a transaction | Proven between opcodes on the straight-line sample. The design can retain the complete geth machine state. | Not possible through public hooks. It can restore state and replay a whole externally controlled frame, but cannot continue the suspended parent after nested `CALL`. | Proven between opcodes on the seven-opcode sample only. |
| EVM/geth correctness | Output and storage match geth in the spike. Spike gas is simplified; a production fork must keep geth's original gas tables and execution functions unchanged. | Strongest immediately: execution remains entirely inside unmodified geth. Replay reproduces output, storage, gas, and traces. | Output, storage, and remaining gas exactly match geth for the sample. Correctness says nothing about unsupported EVM behavior. |
| Nested calls, revert, gas, logs | A full fork can preserve them because it starts from geth, but the 1A spike has not yet demonstrated these cases. A checkpoint must include the entire call stack and StateDB journal position. | Nested `CALL`, revert, out-of-gas, logs, and return data were observed and reproduced by rollback plus whole-frame replay. Exact mid-frame resume is impossible. | `CALL`, revert, logs, and call frames are unsupported. Gas is implemented only for the sample path. |
| Code to maintain | Spike: 265 implementation lines and 81 test lines. A resumable fork touches an estimated eight coupled `core/vm` files, about 3,980 of geth's 10,012 `core/vm` lines. | Spike: 61 implementation lines and 168 test lines. No geth fork; production maintenance surface would be small. | Spike: 299 implementation lines and 76 test lines for only seven opcodes. General support would become a second EVM implementation. |
| Time cost | Checkpoint/restore is `O(stack + memory + returnData + overlay metadata)`. Successful resume can avoid re-executing the transaction prefix. | Snapshot creation is effectively constant-time, while restore follows journaled changes. Recovery still costs `O(frame execution)` because the complete frame is replayed. | Similar checkpoint copy cost to 1A and low execution cost for the tiny sample, but no meaningful production estimate exists until the EVM is reimplemented. |
| Memory cost | One retained checkpoint owns copies of stack, memory, return data, and overlay metadata. Periodic/adaptive retention is required to bound memory. | Lowest checkpoint payload: invocation metadata plus a StateDB snapshot revision. The StateDB journal retains changes until the snapshot is released. | Copies stack, memory, writes, and warm-slot set. Supporting full EVM semantics would add refunds, access lists, logs, transient state, and call frames. |
| Expansion | Technically capable of full EVM resume, but every geth upgrade requires careful merge and differential/fuzz testing. | Easy to keep compatible with geth, but cannot be extended to exact mid-frame resume without becoming direction 1A. | Poor. Every opcode and hard-fork rule must be independently implemented and audited. |

## Selected direction and reason

Choose **1A**. It is the only direction that can satisfy the defining M5
requirement: resume at an opcode checkpoint before the conflicting state read
without replaying the transaction or its parent frame.

Direction 1B has the best compatibility and lowest maintenance cost, but the
spike proves that geth's public hooks do not expose or restore parent PC, stack,
memory, gas, or return-data state. It therefore cannot deliver the required
resume behavior. Direction 1C proves the concept cheaply for seven opcodes, but
extending it would duplicate consensus-critical EVM semantics and carries more
correctness risk than maintaining a focused geth patch.

For M5, the 1A implementation must keep geth opcode and gas semantics intact and
limit the fork to pause/capture/restore plumbing. Acceptance requires
differential and fuzz comparison with the pinned geth version, including nested
calls, revert, out-of-gas, logs, return data, refunds, access lists, and hard-fork
rules. This document makes the decision only; it does not implement M5.2 or any
production code.
